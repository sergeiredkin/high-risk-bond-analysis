- Dashboard redesign ("Купон Лаб", 2026-09, three stages, all landed): `dashboard/template.html` + `dashboard/src/` rebuild the Claude Design reference `bond-lab-design-reference.html` (untracked, primary checkout root; its header comment is the spec). CSS tokens/components in `src/design-system.css` are verbatim; vanilla JS, no framework, one self-contained output file, one page per `src/pages/*.js`. `dashboard/legacy/template.html` is kept buildable on purpose — it is the fallback for the live cutover to this front end; retire it only once the new one has been live and stable.
- `watchlist_tier` is pipeline-only. `issuer.watchlist_tier` is how scrape/financials/universe/portfolio scope their issuer set (plus the `watchlist_tier_log` audit trail and `hybond promote`/`demote`) — removing it breaks the data path. It is deliberately absent from everything the dashboard is handed; ticker-watching reaches the UI as the per-bond `in_watchlist` flag instead. `tests/test_dashboard_pages.py` guards both halves of that boundary.
- D3 (cdnjs) is the dashboard's only external script, for the market map; everything else including the data is inlined. Without it `TerminalMap.mount()` says so and the screener still works — keep that fallback.
- «Ставка и ОФЗ» (`src/pages/rates.js`, fifth route, captain-approved 2026-09-17) is the one page beyond the design reference; it may only use classes that already exist (`tests/test_dashboard_pages.py` enforces it). Its data: `hybond expectations` (CBR forecasts, ОНЕГДКП scenario versions, macro survey, decision documents, daily key rate, calendar — each with its official cbr.ru URL) and `hybond ofz`, both non-fatal steps in `daily_run.sh`. First load of history: `hybond expectations --backfill`. AEY scenarios now come from those publications (`portfolio.get_rate_scenarios`: stress = «Проинфляционный», bull = «Дезинфляционный», `aey_risky` = «Рисковый»); without them it falls back to the old `cbr_meeting` derivation, labelled by `scenario_source`. The meeting schedule is the stored CBR calendar (`cbr_tracker.get_schedule`), not `CBR_MEETINGS_2026`.
- `src/bonds.js` is the one bond model the map, screener, drawer and Портфель read. Percent-vs-fraction is this export's recurring bug class: `pd_rating` is a fraction while `DATA.pd_by_rating` is the same number in percent, and `DATA.portfolios[].allocation` stores `aey_base`/`avg_aey`/`expected_loss`/`net_return` as fractions while `universe_now` carries them in percent. Resolve a position through `BOND_BY_SECID` rather than rendering a stored rate. Also: `DATA.rf_curve` keeps one bond per 0.1-year bucket, so it zigzags wherever that bond carried a fallback `rf_rate_pct` — the real CBR zero curve is `DATA.zcyc` (percent). CBR range cells carry a fused footnote digit («14,5–14,61») and the forecast table's years move every January: parse with `cbr_tracker.parse_rate_range` / `forecast_rate_by_year`, never by column position.
- Never invent a threshold for the dashboard: the design reference's numbers are mock. Real ones come from the pipeline — `portfolio.PRESETS` (exported per portfolio as `constraints`), `yield_zone`, and the cuts in `src/bonds.js`.
- Credit ratings: every consumer goes through `src/hybond/ratings.py` (`resolve()` / `resolved_grade()`), never `db.current_rating()` directly. Source is the free MOEX ISS ЦКИ endpoints (captain: no paid data), refreshed by `hybond refresh-ratings` before `hybond universe`; the legacy `rating` table is fallback/override only. Rating `D` has no PD on purpose. Keep the fetch spacing and incremental TTL (`ratings_pipeline.py`) — production shares this ISS path. DECISIONS.md 2026-09-17 has the rate-limit evidence.
- Every detected rating move (upgrade/downgrade/default/withdrawn/new) is logged to `rating_change` (`store/agency_ratings.py`) and surfaced in the dashboard (header chip, Обзор alert band, screener/drawer/Портфель markers, Данные feed) — see that module's docstring for the baseline rule (a target's first successful fetch records nothing). Adding a column to an already-shipped table needs an explicit migration in `agency_ratings.init()`: `CREATE TABLE IF NOT EXISTS` is a no-op against a table that already exists, so a production DB from before the column existed will otherwise throw "no such column" on the next write — `first_ok_at` on `agency_rating_fetch` hit exactly this and is the pattern to copy for the next one.
- Tests: `python3 -m pytest -q` (whole suite runs in under a minute).
